konomi-ablate

How much of your system prompt is doing nothing — and what is that costing?

Every prompt tool scores a prompt. None of them delete a clause and measure. So prompts accrete: someone adds "think step by step" in March, nobody ever removes it, and you pay for those tokens on every call for the life of the product. This deletes each clause, checks whether the eval actually moved, and puts a bill on the ones that did nothing.

A delta is not a finding

Removing a clause and watching the score drop by one means nothing on twenty items. Every verdict goes through an exact sign test. Movement that doesn't beat a coin is inconclusive, never dead.

Individually removable ≠ jointly removable

Two clauses can each be free to drop alone and disastrous together — each covers for the other. A tool that lists eight dead clauses and lets you delete all eight told you something it never measured. This refuses to certify until the joint run is done.

A flat total hides a safety move

Deleting a safety clause because the aggregate didn't budge is the same poison as picking a preference pair on aggregate. A clause that moves a protected axis is never dead.

Why leave-one-out alone is dangerous

Imagine two clauses: "cite your sources" and "never state anything you cannot support". They overlap. Remove either one and the other carries the load — so each looks free. Remove both and grounding collapses.

Leave-one-out ablation reports both as dead, because that is literally what it measured. The measurement is correct and the conclusion people draw from it — "so I can delete both" — is not, and nothing in the output warns them.

So a candidate set here is never certified until the joint variant has actually been run. Switch the joint run to broke on the previous tab and watch the batch get refused even though every clause in it was individually dead.

The loop

import { plan, analyse } from './ablate.mjs';
import { headline } from './cost.mjs';

// 1 · plan the runs — a rendered baseline plus one variant per clause
const p = plan(mySystemPrompt, { strategy: 'line' });

// 2 · YOU run your eval on p.baseline.prompt and each p.variants[i].prompt.
//     Scores are per item, in the same order. Numbers, or konomi-rubric vectors
//     (vectors additionally enable the protected-axis check).
const results = { baseline: [...], 'without-0': [...], ... };

// 3 · analyse
const report = analyse(p, results);
report.candidates    // individually removable
report.certified     // [] until the joint run is done and holds

// 4 · the joint run — the step nobody does
const p2 = plan(mySystemPrompt, { jointOmit: report.candidates });
// run the one extra variant, add it as results.joint, analyse again
headline(analyse(p2, results2), { callsPerMonth: 40000, pricePerMillion: 3 }).sentence

Nothing here calls a model. Your harness runs the evals and hands back scores, which keeps the kernel pure, lets it work with any model, and is what makes the significance test possible at all.

Honest limits

  • This is only as good as your eval. If your corpus does not discriminate, every clause reads as dead. That is a finding about the corpus, and the tool reports inconclusive rather than dead when nothing moved decisively.
  • The joint run tests one specific batch. Certifying {A,B,C} says nothing about {A,B,D}. Interaction is combinatorial and this checks the set you actually propose to delete.
  • Token counts are estimated at roughly ±20% unless you supply an exact tokeniser. The money figure is rounded to the precision that estimate supports rather than printed to the penny.
  • Ablation measures effect on your eval. A clause that guards against something your corpus never contains will read as dead and may still be load-bearing in production.
  • HARMFUL is a real verdict. Some clauses make output measurably worse; nobody looks for them because nobody deletes clauses to find out.
